# 0006. 取得は1時間ごとにまとめて書き、DTS はその日の分を入れ直す

- 日付: 2026-10-05
- ステータス: 承認
- 置き換え: ADR 0001 の「5分ごとに起動して30秒間隔×10回」、ADR 0005 の「APPEND」

## 要約

GCS の書き込み回数を無料枠（月5,000回）に収めるため、取得は1時間に1回起動して約54分間取り続け、最後に1回だけ書く。DTS は1時間ごとに「その日のフォルダ」だけを MIRROR で入れ直す。

## 背景

費用は0円が絶対条件（AGENTS.md）。GCS の無料枠は Class A（書き込み・一覧）が月5,000回、Class B（読み取り）が月5万回（https://cloud.google.com/free/docs/free-cloud-features 、2026-10-04 に確認）。

これまでの作りでは Class A が月約1.9万回になり、無料枠の約3.7倍だった。

| 操作 | 回数 / 月 |
|---|---|
| 取得の書き込み（5分ごとに raw と meta の2ファイル） | 約17,300 |
| DTS の一覧（1時間ごと × 2設定） | 約1,440 |

さらに DTS が `raw/` 全体を一覧すると、ファイルが増えるほど1回の一覧が複数ページ（1ページ最大1,000件）に分かれ、回数が増え続ける。

## 選択肢

| 案 | Class A / 月 | 良い点 | 気になる点 |
|---|---|---|---|
| **1. 1時間分ためて1回で書く** | 約3,000（DTS 込み） | 「正本は GCS」（ADR 0005）を保てる | 1回の失敗で1時間分が欠ける |
| 2. GCS を通さず BigQuery に直接ロード | 書き込み 0 | 一番単純 | ADR 0005 を作り直す。BigQuery の30日の有効期限を外す必要がある |
| 超過を認める（月約10円） | — | 何も変えない | 0円の条件に反する |

## 決定

取得:

- Cloud Scheduler `opensky-ingest-dispatch` を毎時0分（UTC）にする
- 1回の実行で30秒間隔×108回（約54分）取得し、最後に raw と meta を1つずつ書く。ファイルは1時間枠（`raw/dt=YYYY-MM-DD/hh=HH/YYYYMMDDTHH00Z.jsonl.gz`）
- OpenSky のトークンは30分で切れるため、25分たったら取り直す。401 が返ったら次の取得で取り直す

DTS（ADR 0005 の書き込みの設定を置き換え）:

- 毎時30分に実行する
- 転送元は実行時パラメータで、その日のフォルダだけにする: `gs://opensky-data-platform-raw/raw/dt={run_time-1h|"%Y-%m-%d"}/*/*`（`*` はフォルダをまたがないので、`hh=HH/` の分と合わせて2つ）
- 書き込みは MIRROR、転送先はその日のパーティション: `<テーブル>${run_time-1h|"%Y%m%d"}`。毎回その日の分を丸ごと入れ直す
- meta も同じ形でもう1つ作る

## 理由

- 案1は書き込みが月 24回 × 2 × 31日 = 1,488回、DTS の一覧が 24回 × 2設定 × 31日 = 1,488回（その日のフォルダは24ファイルなので毎回1ページ）で、合計約3,000回。無料枠に余裕がある
- DTS の APPEND は「前回の成功以降に更新されたファイル」だけを読む。転送元をその日のフォルダに絞ると、日付の変わり目に書かれたファイルが「前回より古い」扱いになり、取りこぼす。MIRROR でその日の分を毎回入れ直せば取りこぼさない
- MIRROR では同じ枠をやり直しても上書きになるので、BigQuery に重複が入らない（ADR 0005 の「dbt で重複を除く」が不要になる）
- `run_time-1h` にすることで、0時30分の実行は前日のフォルダを見る。23時台のファイル（23時56分ごろに書かれる）を前日のパーティションに入れられる
- GitHub Actions の負荷は今と同じ（4分40秒 × 288回 ≒ 54分 × 24回 ≒ 22時間/日）。起動回数が減るので、規約の懸念（ADR 0003）は強まらない
- 案2は「正本を GCS に残し、BigQuery は30日で消す」を崩すため外した

## 費用の確認（月31日、無料枠と比べて）

| 操作 | 回数 / 月 | 無料枠 |
|---|---|---|
| GCS Class A（書き込み＋一覧） | 約3,000 | 5,000 |
| GCS Class B（DTS がその日のファイルを毎回読む: 平均12ファイル × 24回 × 2設定） | 約18,000 | 50,000 |
| GCS の保存（月約70MB ずつ増える） | — | 5GB（約6年分） |
| BigQuery のロード（DTS） | 1日48ジョブ | 無料（上限はテーブルごとに1日1,500） |
| OpenSky のクレジット | 108回 × 24 = 2,592/日 | 4,000/日 |

## 影響・見直し条件

- 1時間分が1ファイルになるため、実行が失敗すると1時間分が欠ける。meta の失敗率と欠けた枠の数を見て、多ければ「30分ごとに書く」（Class A 約4,500回）を検討する
- 23時台のファイルの書き込みが0時30分より遅れると、前日のパーティションに入らない（GCS には残る）。そのときは DTS を手動で前日分だけ実行し直す
- 5分間隔のころのファイル（`<YYYYMMDDTHHMM>Z`、2026-10-04〜05）は同じフォルダに残る。MIRROR で一緒に読まれるが、行の中身（`fetched_at`）は同じ形なので問題ない
- Cloud Scheduler の切り替えは、コードを main に入れる前に行う。5分ごとのまま新しいコード（約54分の実行）が動くと、実行が重なり同じ1時間枠のファイルを上書きしてしまう
