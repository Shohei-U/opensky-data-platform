# ADR（Architecture Decision Record）の読み方・書き方

ADR は「なぜこの作りにしたか」を1つの判断につき1ページで残すメモ。コードを見れば「何をしたか」は分かるが、「なぜそうしたか」「他に何を考えたか」は残らない。それを残すのが ADR。

2011年に Michael Nygard が提案した形が元になっている（https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions ）。チーム開発で広く使われていて、まとまった資料は https://adr.github.io/ にある。

## なぜ書くか

1. **後から思い出せる**: 3か月後の自分は、今日の理由を覚えていない
2. **同じ議論を繰り返さない**: 「DTS じゃなくて外部テーブルでよくない？」と思ったら、ADR を読めば検討済みかどうか分かる
3. **見直しの合図が分かる**: 「こうなったら見直す」を書いておくと、前提が崩れたときに気づける

## いつ書くか（このリポジトリの基準）

| 書く | 書かない |
|---|---|
| 後から戻しにくい判断（データの置き場所、どこで動かすか、スキーマ、費用に関わる構成） | 小さな調整（設定値、名前、ドキュメント）→ PR の本文に理由を書くだけ |
| 選択肢が2つ以上あって、選ばなかった理由も残したいもの | 選択肢が実質1つしかないもの |

進め方: まず会話で「図1枚＋問い1つ＋案2〜3個」を見て本人が決める → 決めた後にエージェントが ADR を書く。

## 読み方（見出しの意味）

| 見出し | 何が書いてあるか | 読むときの問い |
|---|---|---|
| 要約 | 1〜2行で、何をどう決めたか | まずここだけ読めばよい |
| 背景 | なぜ判断が必要になったか。制約や実測値 | 何が困っていたのか？ |
| 選択肢 | 比べた案と、それぞれの良い点・気になる点 | 他にどんな手があったか？ |
| 決定 | 選んだ案 | 結局どうしたか？ |
| 理由 | 選んだ理由と、他を選ばなかった理由 | なぜそれか？ |
| 影響・見直し条件 | 決めたことで起きること、どうなったら見直すか | 何に気をつければよいか？ |

## ステータス

- **提案**: 案を出した段階。まだ決まっていない
- **承認**: 決まった。この通りに作る
- **置き換え**: 後の ADR で変わった。新しい ADR の番号を書く（古い ADR は消さずに残す。判断の歴史になるため）

## 書き方（テンプレート）

```markdown
# NNNN. 決めたことを一文で

- 日付: YYYY-MM-DD
- ステータス: 承認
- 置き換え: （あれば）ADR NNNN のうち〇〇の部分

## 要約

1〜2行。何をどう決めたか。

## 背景

判断が必要になった理由。制約（費用0円など）と実測値。

## 選択肢

| 案 | 良い点 | 気になる点 |
|---|---|---|

## 決定

## 理由

選ばなかった案の理由も1行ずつ。

## 影響・見直し条件

- こうなったら見直す
```

## よくある失敗

- **理由を書かない**: 「DTS にした」だけでは、後から読んでも役に立たない
- **選ばなかった案を書かない**: 同じ検討をもう一度することになる
- **古い ADR を書き換える**: 判断が変わったら新しい ADR を作り、古い方のステータスを「置き換え」にする
- **長すぎる**: 1ページを超えたら、判断が2つ混ざっていないか疑う
