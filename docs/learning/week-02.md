# 第2週: 5分ごとに自動で貯まる

取り込み層を「手元で1回動くスクリプト」から「クラウドで自動で動くジョブ」にする週。

```
#7 繰り返し取得 → #8 リトライ → #9 GCS へ書く → #10 コンテナ・Cloud Run → 遮断が判明 → 取得は GitHub Actions へ（ADR 0003）
→ リポジトリを Public に作り直し（#31）→ #29 Workload Identity Federation → #28 失敗ログ → #30 定期実行
```

## #7 30秒間隔×10回の取得を1ファイルに

| 学んだこと | 中身 |
|---|---|
| 間隔は起動時刻から測る | `sleep(start + i*interval - now)`。「前回の終わりから30秒」だと、取得にかかった時間の分だけ開始がずれていく |
| 待ち時間には monotonic を使う | `time.monotonic()` は必ず増える経過時間。壁時計（`datetime.now()`）は NTP の補正で飛ぶことがあるので、記録用の時刻だけに使う |
| 依存性の注入でテストを速くする | `sleep` と時計を引数で受け取るようにすると、テストでは偽物を渡して「30秒待ったか」を一瞬で確かめられる |
| 1回の失敗で全体を止めない | 10回のうち1回が失敗しても、メタに記録して残りを続ける。データの欠けは最小にする |

ADP: —（実装の基礎）

## #8 リトライと 429 バックオフ

| 学んだこと | 中身 |
|---|---|
| 失敗には種類がある | 待てば直る（5xx・タイムアウト）／待つ時間が決まっている（429）／何度やっても同じ（4xx）で、対応を分ける |
| 指数バックオフ | 再試行の間隔を 1秒 → 2秒 → 4秒 と倍にする。弱ったサーバーを叩き続けず、回復する時間を作る |
| 上限を決める | 回数（3回）と待ち時間（30秒）に上限を付ける。「1時間後に戻る」と言われたら、待たずに諦める |
| 試行回数を記録する | `attempts` をメタに残すと、後で「リトライがどれくらい起きているか」を集計できる |

ADP: パイプラインのオーケストレーション（リトライ・失敗時の扱い）

## #9 GCS へ直接書き込む

| 学んだこと | 中身 |
|---|---|
| ADC（Application Default Credentials） | コードに認証情報を書かず、ライブラリが自動で探す。手元は個人用 ADC、Cloud Run 上はサービスアカウント。同じコードで両方動く |
| GCS のオブジェクトは追記できない | 丸ごと書き直すしかない。だからメタも「1回の起動 = 1ファイル」にした |
| 冪等性 | ファイル名を5分枠にして、同じ枠のやり直しは上書きにした。何度実行しても結果が同じになる |
| 出力先の抽象化 | `data` なら手元、`gs://…` なら GCS。テストでは GCS を偽物に差し替える |
| パーティション分けしたパス | `raw/dt=YYYY-MM-DD/hh=HH/`。BigQuery から日付で絞って読める形（第3週につながる） |

ADP: データの準備と取り込み（GCS・バッチ取り込み・パスの設計）、データの管理（認証）

## #10 Docker 化 → Cloud Run Jobs（デプロイまで完了。OpenSky への接続が遮断されて取得は失敗）

| 学んだこと | 中身 |
|---|---|
| コンテナ | コードと Python・ライブラリを1つのイメージに詰める。どこで動かしても同じ環境になる |
| CPU アーキテクチャ | Mac（Apple Silicon）は arm64、Cloud Run は amd64。`--platform linux/amd64` で作る |
| イメージを小さく・再現可能に | slim のベース、依存を先に入れてキャッシュを効かせる、ベースはダイジェストで固定、非 root で実行 |
| Jobs と Service | Jobs は実行したら終わる（動いた時間だけ課金）。Service は常に待ち受ける。定期的なバッチには Jobs |
| サービスアカウントと最小権限 | ジョブ専用のアカウントに、このバケットだけの権限を付ける。漏れたときの影響を小さくする |
| 秘密情報の管理 | 認証情報は Secret Manager に置き、ファイルとしてマウントする。環境変数に平文で置くと Console から見えてしまう |
| ログは1行の JSON | Cloud Logging は1行を1件として扱う。`severity` と `message` を入れると構造化ログになり、絞り込みや集計がしやすい |
| 2段階のリトライ | アプリの中（#8、数秒の揺らぎ）と、ジョブの再試行（`--max-retries`、プロセスごと落ちたとき）で役割を分ける |

ADP: パイプラインのオーケストレーション（Cloud Run Jobs）、データの管理（IAM・Secret Manager）

### #10 で起きたこと（障害の切り分け）

| 段階 | やったこと | 分かったこと |
|---|---|---|
| 症状 | Cloud Run のジョブが2回とも `exit(1)` | ログに `ConnectTimeout`（`auth.opensky-network.org:443`） |
| ログを読む | トレースバックの一番下（根本）を見る | `sock.connect` で時間切れ。認証の失敗（401）ではなく、接続の手前で止まっている |
| 場所を変えて試す | Cloud Shell と GitHub Actions から `curl` | GCP は `000`、GitHub Actions は `200`。違いは「どこから接続したか（IP）」だけ |
| 一次情報で裏付け | OpenSky の README | 大手クラウドの IP をブロックすることがある、と明記されている |

| 学んだこと | 中身 |
|---|---|
| 症状と原因を分ける | 「ジョブが落ちた」は症状。ログ → 再現 → 比較 で「GCP の IP が遮断されている」まで絞り込む |
| 比較実験 | 同じコード・同じ認証情報で、場所だけ変えて試すと、原因を1つに絞れる |
| 外部 API はクラウドから遮断されることがある | データソースの利用条件（接続元の制限）は、設計の前に確認する |
| 失敗時のログも1行にする | 成功は1行の JSON になったが、失敗はトレースバックが8件に分かれた。例外を捕まえて `severity: ERROR` の1行で出すのが次の改善 |
| Error Reporting | stderr のトレースバックは、自動で「エラーのグループ」にまとめられ、発生回数が見られる |

ADP: パイプラインのオーケストレーション（Cloud Run Jobs・再試行）、データの管理（IAM・Secret Manager）、Cloud Logging と Error Reporting

## #31 リポジトリを Public に作り直す

| 学んだこと | 中身 |
|---|---|
| git の履歴は消しにくい | ファイルを直しても、過去の commit から読める。GitHub では、履歴を書き換えても PR の中に古い commit が残る |
| 公開前に見る場所はファイルだけではない | commit の履歴・Issue・コメント・**編集履歴**・PR も公開される。Issue の編集履歴は、版ごとに削除できる |
| 作り直しの手順 | 今の状態から親のない commit を1つ作って新しいリポジトリへ。Issue は Transfer で移す（コメント・ラベル・マイルストーン・親子関係・ボードも付いてくる。反映は少し遅れる） |
| 手元だけの情報の置き場 | 環境やアカウントの情報は git の管理外のファイル（`AGENTS.local.md`）に分ける |
| ブランチ保護 | Public（または有料プラン）で使える。PR 必須・CI 必須・直線の履歴・force push 禁止・管理者にも適用 |

ADP: —（リポジトリ運用）

## #29 Workload Identity Federation

| 学んだこと | 中身 |
|---|---|
| 鍵ファイルを置かない認証 | GitHub が署名した ID トークンを、STS が GCP の短命なトークンに交換する。期限のない JSON キーを Secrets に置くより安全 |
| プールとプロバイダ | プール = 外部の ID の入れ物、プロバイダ = どの発行元（GitHub）を信用するか。属性の対応付け（attribute mapping）と条件（attribute condition）で、受け入れる相手を絞る |
| 名前ではなく ID で絞る | リポジトリ名は変えられる。`repository_id` なら、同じ名前のリポジトリを別に作られても通らない |
| ブランチで絞る | `ref == refs/heads/main` で、Public リポジトリへの他人の PR から書かれるのを防ぐ |
| 有効化の反映には時間がかかる | API を有効にした直後は、IAM の操作が `PERMISSION_DENIED` になることがある。少し待って再実行すると通った。だからスクリプトは「何度実行しても大丈夫」に作る |

ADP: データの管理（IAM・サービスアカウント・外部からの認証）

## #28 失敗時のログを1行の JSON にする

| 学んだこと | 中身 |
|---|---|
| 最上位で例外を捕まえる | `main()` の一番外で例外を捕まえ、`severity: ERROR` の1行を出して終了コード 1 で終わる。トレースバックが何件にも分かれず、「エラーを数える」「種類で絞る」ができる |
| 終了コードで失敗を伝える | 1行のログにしても `exit 1` は残す。GitHub Actions も Cloud Run も、終了コードでジョブの成否を判断する |
| リトライを部品にする | 取得用だった `fetch_with_retry` を `call_with_retry` に一般化し、トークンの取得にも同じ判断（5xx・タイムアウトは再試行、401 は即座に諦める）を使う |
| ジェネリクス（Python 3.12） | `class RetryOutcome[T]` / `def call_with_retry[T](...)`。何を返す処理でも、型を保ったまま包める |
| 失敗をわざと起こして確かめる | 間違った認証情報で実行し、`401` が1行の ERROR になり、リトライされないことを見た |

ADP: パイプラインのオーケストレーション（失敗の検知・再試行）、Cloud Logging（構造化ログ・severity）

## #30 5分ごとの取得ワークフロー（GitHub Actions）

| 学んだこと | 中身 |
|---|---|
| schedule と workflow_dispatch | cron（`*/5 * * * *`）で定期実行、`workflow_dispatch` で手動実行。最初の定期実行は、追加してから動き出すまで時間がかかることがある |
| `id-token: write` | ワークフローに GitHub の ID トークンを発行させる許可。これがないと Workload Identity Federation が使えない |
| concurrency | 同じグループのジョブを同時に動かさない。前の実行が長引いても、同じ5分枠のファイルを取り合わない |
| Secrets | OpenSky の認証情報は暗号化して保存され、登録後は誰も値を見られない。ログに出ても `***` に置き換えられる |
| main でしか確かめられないもの | Workload Identity Federation の条件を main に絞ったので、PR のブランチからは GCS に書けない。merge してから main で手動実行して確かめる |
| 最初の本番の結果 | 10回の取得・60行・すべて 200・リトライなし。`raw/dt=2026-10-04/hh=07/20261004T0715Z.jsonl.gz`（2KB） |

ADP: パイプラインのオーケストレーション（スケジュール実行・同時実行の制御・タイムアウト）、データの管理（外部からの認証・秘密情報）

## 第2週のまとめ

```
手元で1回動くスクリプト
  → 繰り返し取得・リトライ・GCS 出力（#7〜#9）
  → コンテナ化して Cloud Run へ（#10）→ OpenSky が GCP を遮断していると判明
  → 取得を GitHub Actions へ（ADR 0003）、Public に作り直し（#31）
  → 鍵なし認証（#29）・失敗ログの1行化（#28）・5分ごとの定期実行（#30）
```

一番の学び: **計画どおりにいかないときは、症状 → ログ → 比べる実験 → 一次情報の順で原因を確定させ、設計を見直して ADR に残す**。
