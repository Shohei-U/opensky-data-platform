# 第2週: 5分ごとに自動で貯まる

取り込み層を「手元で1回動くスクリプト」から「クラウドで自動で動くジョブ」にする週。

```
#7 繰り返し取得 → #8 リトライ → #9 GCS へ書く → #10 コンテナ・Cloud Run → 遮断が判明 → 取得は GitHub Actions へ（ADR 0003）
```

## #7 30秒間隔×10回の取得を1ファイルに

| 学んだこと | 中身 |
|---|---|
| 間隔は起動時刻から測る | `sleep(start + i*interval - now)`。「前回の終わりから30秒」だと、取得にかかった時間の分だけ開始がずれていく |
| 待ち時間には monotonic を使う | `time.monotonic()` は必ず増える経過時間。壁時計（`datetime.now()`）は NTP の補正で飛ぶことがあるので、記録用の時刻だけに使う |
| 依存性の注入でテストを速くする | `sleep` と時計を引数で受け取るようにすると、テストでは偽物を渡して「30秒待ったか」を一瞬で確かめられる |
| 1回の失敗で全体を止めない | 10回のうち1回が失敗しても、メタに記録して残りを続ける。データの欠けは最小にする |

ADP: —（実装の基礎）

## #8 リトライと 429 バックオフ

| 学んだこと | 中身 |
|---|---|
| 失敗には種類がある | 待てば直る（5xx・タイムアウト）／待つ時間が決まっている（429）／何度やっても同じ（4xx）で、対応を分ける |
| 指数バックオフ | 再試行の間隔を 1秒 → 2秒 → 4秒 と倍にする。弱ったサーバーを叩き続けず、回復する時間を作る |
| 上限を決める | 回数（3回）と待ち時間（30秒）に上限を付ける。「1時間後に戻る」と言われたら、待たずに諦める |
| 試行回数を記録する | `attempts` をメタに残すと、後で「リトライがどれくらい起きているか」を集計できる |

ADP: パイプラインのオーケストレーション（リトライ・失敗時の扱い）

## #9 GCS へ直接書き込む

| 学んだこと | 中身 |
|---|---|
| ADC（Application Default Credentials） | コードに認証情報を書かず、ライブラリが自動で探す。手元は個人用 ADC、Cloud Run 上はサービスアカウント。同じコードで両方動く |
| GCS のオブジェクトは追記できない | 丸ごと書き直すしかない。だからメタも「1回の起動 = 1ファイル」にした |
| 冪等性 | ファイル名を5分枠にして、同じ枠のやり直しは上書きにした。何度実行しても結果が同じになる |
| 出力先の抽象化 | `data` なら手元、`gs://…` なら GCS。テストでは GCS を偽物に差し替える |
| パーティション分けしたパス | `raw/dt=YYYY-MM-DD/hh=HH/`。BigQuery から日付で絞って読める形（第3週につながる） |

ADP: データの準備と取り込み（GCS・バッチ取り込み・パスの設計）、データの管理（認証）

## #10 Docker 化 → Cloud Run Jobs（デプロイまで完了。OpenSky への接続が遮断されて取得は失敗）

| 学んだこと | 中身 |
|---|---|
| コンテナ | コードと Python・ライブラリを1つのイメージに詰める。どこで動かしても同じ環境になる |
| CPU アーキテクチャ | Mac（Apple Silicon）は arm64、Cloud Run は amd64。`--platform linux/amd64` で作る |
| イメージを小さく・再現可能に | slim のベース、依存を先に入れてキャッシュを効かせる、ベースはダイジェストで固定、非 root で実行 |
| Jobs と Service | Jobs は実行したら終わる（動いた時間だけ課金）。Service は常に待ち受ける。定期的なバッチには Jobs |
| サービスアカウントと最小権限 | ジョブ専用のアカウントに、このバケットだけの権限を付ける。漏れたときの影響を小さくする |
| 秘密情報の管理 | 認証情報は Secret Manager に置き、ファイルとしてマウントする。環境変数に平文で置くと Console から見えてしまう |
| ログは1行の JSON | Cloud Logging は1行を1件として扱う。`severity` と `message` を入れると構造化ログになり、絞り込みや集計がしやすい |
| 2段階のリトライ | アプリの中（#8、数秒の揺らぎ）と、ジョブの再試行（`--max-retries`、プロセスごと落ちたとき）で役割を分ける |

ADP: パイプラインのオーケストレーション（Cloud Run Jobs）、データの管理（IAM・Secret Manager）

### #10 で起きたこと（障害の切り分け）

| 段階 | やったこと | 分かったこと |
|---|---|---|
| 症状 | Cloud Run のジョブが2回とも `exit(1)` | ログに `ConnectTimeout`（`auth.opensky-network.org:443`） |
| ログを読む | トレースバックの一番下（根本）を見る | `sock.connect` で時間切れ。認証の失敗（401）ではなく、接続の手前で止まっている |
| 場所を変えて試す | Cloud Shell と GitHub Actions から `curl` | GCP は `000`、GitHub Actions は `200`。違いは「どこから接続したか（IP）」だけ |
| 一次情報で裏付け | OpenSky の README | 大手クラウドの IP をブロックすることがある、と明記されている |

| 学んだこと | 中身 |
|---|---|
| 症状と原因を分ける | 「ジョブが落ちた」は症状。ログ → 再現 → 比較 で「GCP の IP が遮断されている」まで絞り込む |
| 比較実験 | 同じコード・同じ認証情報で、場所だけ変えて試すと、原因を1つに絞れる |
| 外部 API はクラウドから遮断されることがある | データソースの利用条件（接続元の制限）は、設計の前に確認する |
| 失敗時のログも1行にする | 成功は1行の JSON になったが、失敗はトレースバックが8件に分かれた。例外を捕まえて `severity: ERROR` の1行で出すのが次の改善 |
| Error Reporting | stderr のトレースバックは、自動で「エラーのグループ」にまとめられ、発生回数が見られる |

ADP: パイプラインのオーケストレーション（Cloud Run Jobs・再試行）、データの管理（IAM・Secret Manager）、Cloud Logging と Error Reporting
